# DTS Tasks API

A REST API that lets HMCTS caseworkers create, track and manage their tasks.

Built for the [DTS Developer Technical Test](https://github.com/hmcts/dts-developer-challenge).

- **Runtime:** Node.js 20.11+ and TypeScript
- **Framework:** Express 5
- **Database:** SQLite via `better-sqlite3` (file-backed, zero setup)
- **Validation:** Zod schemas with structured error responses
- **Docs:** OpenAPI 3.0 specification served through Swagger UI
- **Tests:** Vitest + Supertest, 47 tests, ~88% coverage

---

## Quick start

```bash
npm install
cp .env.example .env
npm run seed     # optional: adds five demo tasks
npm run dev      # http://localhost:3000
```

Then open:

| URL                            | Description              |
| ------------------------------ | ------------------------ |
| http://localhost:3000/docs     | Swagger UI (interactive) |
| http://localhost:3000/openapi.json | Raw OpenAPI document |
| http://localhost:3000/health   | Health check             |

### Scripts

| Command                 | Description                                     |
| ----------------------- | ----------------------------------------------- |
| `npm run dev`           | Run the API in watch mode with `tsx`            |
| `npm run build`         | Compile TypeScript to `dist/`                   |
| `npm start`             | Run the compiled API                            |
| `npm test`              | Run the test suite once                         |
| `npm run test:watch`    | Run tests in watch mode                         |
| `npm run test:coverage` | Run tests with a coverage report                |
| `npm run typecheck`     | Type-check without emitting output              |
| `npm run seed`          | Insert demo tasks into the configured database  |

### Run with Docker

```bash
docker build -t dts-tasks-api .
docker run -p 3000:3000 -v "$PWD/data:/app/data" dts-tasks-api
```

The SQLite file lives in `./data` and is mounted as a volume so data survives
container restarts.

## API

All responses are JSON. Success payloads are wrapped in `{ "data": ... }`;
errors use a consistent `{ "error": { "code", "message", "details"? } }` shape.

### Task model

| Field         | Type                                       | Notes                                   |
| ------------- | ------------------------------------------ | --------------------------------------- |
| `id`          | string (UUID)                              | Generated by the API                    |
| `title`       | string, 1–200 characters                   | Required                                |
| `description` | string, ≤2000 characters, or `null`        | Optional                                |
| `status`      | `TODO` \| `IN_PROGRESS` \| `DONE`          | Defaults to `TODO` on create            |
| `dueDateTime` | ISO 8601 date-time (UTC)                   | Required; must include a timezone or `Z` |
| `createdAt`   | ISO 8601 date-time (UTC)                   | Generated by the API                    |
| `updatedAt`   | ISO 8601 date-time (UTC)                   | Generated by the API                    |

### Endpoints

| Method   | Path                      | Description                          |
| -------- | ------------------------- | ------------------------------------ |
| `GET`    | `/api/tasks`              | List tasks, ordered by due date      |
| `POST`   | `/api/tasks`              | Create a task                        |
| `GET`    | `/api/tasks/:id`          | Retrieve a task by ID                |
| `PATCH`  | `/api/tasks/:id`          | Update one or more fields            |
| `PATCH`  | `/api/tasks/:id/status`   | Update only the status               |
| `DELETE` | `/api/tasks/:id`          | Delete a task                        |
| `GET`    | `/health`                 | Health and database check            |

`GET /api/tasks` supports two optional query parameters:

- `status` — filter by `TODO`, `IN_PROGRESS` or `DONE`
- `search` — case-insensitive search across title and description

Unknown query parameters and unknown body fields are rejected with `400`, so
typos fail loudly instead of being silently ignored.

### Examples

Create a task:

```bash
curl -i -X POST http://localhost:3000/api/tasks \
  -H 'Content-Type: application/json' \
  -d '{
    "title": "Review case file for hearing",
    "description": "Check the bundle is complete.",
    "status": "TODO",
    "dueDateTime": "2026-12-01T09:30:00Z"
  }'
```

```http
HTTP/1.1 201 Created
Location: /api/tasks/3f1c2a9e-8b7d-4c6a-9e21-5d4f8b0c1a2e
Content-Type: application/json

{
  "data": {
    "id": "3f1c2a9e-8b7d-4c6a-9e21-5d4f8b0c1a2e",
    "title": "Review case file for hearing",
    "description": "Check the bundle is complete.",
    "status": "TODO",
    "dueDateTime": "2026-12-01T09:30:00.000Z",
    "createdAt": "2026-11-01T09:00:00.000Z",
    "updatedAt": "2026-11-01T09:00:00.000Z"
  }
}
```

List and filter:

```bash
curl 'http://localhost:3000/api/tasks?status=TODO&search=hearing'
```

Update a status:

```bash
curl -X PATCH http://localhost:3000/api/tasks/<id>/status \
  -H 'Content-Type: application/json' \
  -d '{"status": "IN_PROGRESS"}'
```

Delete:

```bash
curl -i -X DELETE http://localhost:3000/api/tasks/<id>
# HTTP/1.1 204 No Content
```

Validation error example:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request body contains invalid data.",
    "details": [
      { "field": "title", "message": "title must not be empty." },
      {
        "field": "dueDateTime",
        "message": "dueDateTime must be a valid ISO 8601 date-time, e.g. 2026-12-01T17:00:00Z."
      }
    ]
  }
}
```

| Status | When                                                          |
| ------ | ------------------------------------------------------------- |
| `200`  | Successful read or update                                     |
| `201`  | Task created (with `Location` header)                         |
| `204`  | Task deleted                                                  |
| `400`  | Validation failure or malformed JSON                          |
| `404`  | Task or route not found                                       |
| `500`  | Unexpected server error (details are logged, not returned)    |
| `503`  | `/health` reports the database as unavailable                 |

## Project structure

```
src/
  app.ts                  Express app factory (middleware + routes)
  server.ts               Process entry point, graceful shutdown
  config.ts               Environment configuration
  errors.ts               Typed application errors
  openapi.ts              OpenAPI 3.0 document
  db/database.ts          SQLite connection + schema bootstrap
  middleware/
    validate.ts           Zod body/query validation middleware
    error-handler.ts      Consistent JSON error responses
    request-logger.ts     Structured request logging
  tasks/
    task.types.ts         Domain types and status enum
    task.schemas.ts       Request validation and normalisation
    task.repository.ts    SQL data access
    task.service.ts       Business logic
    task.routes.ts        HTTP layer
tests/
  task.service.test.ts    Service/unit tests against an in-memory DB
  tasks.api.test.ts       End-to-end HTTP tests with Supertest
```

The layers are deliberately separated: routes deal with HTTP, the service holds
business rules, and the repository owns SQL. That keeps the service testable
without booting a server, and makes it straightforward to swap SQLite for
another store later.

### Design decisions

- **SQLite over an external database** keeps the test self-contained: clone,
  `npm install`, `npm run dev`. The repository layer isolates SQL, so moving to
  PostgreSQL would only touch `db/` and `task.repository.ts`.
- **Prepared statements everywhere** — all user input is bound as a parameter,
  including `LIKE` patterns, where `%` and `_` are escaped.
- **Zod at the edge** — every request body and query string is parsed and
  normalised before it reaches the service. Due dates are converted to UTC to
  keep ordering correct regardless of the caller's timezone.
- **Strict schemas** reject unknown fields, so client bugs surface as `400`s.
- **Errors carry stable codes** (`VALIDATION_ERROR`, `TASK_NOT_FOUND`, …) so the
  frontend can react to them without parsing messages.
- **No ORM** — four queries do not justify the indirection; the SQL is explicit
  and fully covered by tests.
- **Helmet + CORS + 100 kB body limit** are enabled by default.

## Testing

```bash
npm test              # 47 tests
npm run test:coverage # coverage report in coverage/
```

The suite covers:

- creating tasks, defaults and persistence
- due-date ordering, status filtering and text search
- partial updates, including clearing a description
- delete semantics
- 404s for unknown tasks and routes
- validation: missing/blank/oversized titles, invalid statuses, dates without a
  timezone, unknown fields, malformed JSON and empty update bodies
- health check, OpenAPI document and Swagger UI availability

HTTP tests run against a real Express app backed by an in-memory SQLite
database, so there is no mocking of the data layer.
